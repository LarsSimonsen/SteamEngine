# Steam Engine Cloudflare Pages Publishing

Publish only the validated Cloudflare artifact generated by this repository.
Keep deployment credentials outside the repository and verify the production
alias before claiming that a release is live.

## Fixed deployment target

- Pages project: `steam-engine`
- Production branch: `main`
- Production alias: `https://steam-engine.pages.dev`
- Artifact: `.build-runs/cloudflare-artifact/`

Do not upload the repository root, a Vite intermediate directory, or the local
IIS slots.

## What this deploys

This skill deploys only the frontend. The calculators call the calculation
API, a separate Cloudflare Worker at
`https://steam-engine-api.lars-simonsen.workers.dev`, directly from the browser
through the adapters in `src/pages/<route>/api.ts` and
`src/pages/encyclopedia/material-tfr-api.ts`. That Worker is proprietary and is
deployed from its own private repository, never by this skill.

Blog posts are not in this repository either; the build reads them from
`STEAM_ENGINE_BLOG_CONTENT` or the gitignored `.blog-content` link (see
`README.md`).

## Refresh command knowledge

Load the Cloudflare Wrangler skill and retrieve the current Pages Direct Upload
documentation before changing Wrangler commands or deployment configuration.
Require Wrangler 4 or newer:

```powershell
npx wrangler --version
```

## Authenticate with least privilege

Check the current identity with `npx wrangler whoami`. If login is needed, use
only the scopes required for Pages deployment and store the token in the native
credential store:

```powershell
npx wrangler login `
  --scopes account:read `
  --scopes user:read `
  --scopes pages:write `
  --use-keyring
```

Do not request Full access or select every available permission. Do not commit
OAuth tokens, API tokens, `.dev.vars`, or Wrangler credential files. Stop and
ask before broadening permissions beyond the three scopes above.

## Build the deployment artifact

Run the repository-owned Cloudflare build:

```powershell
npm run build:cloudflare
```

This command must finish successfully before deployment. It performs the full
frontend build, route-contract validation, generated-link validation, and the
Cloudflare artifact test. It then:

- removes the local-only `web.config`;
- converts directory-index blog and legacy pages to the slashless layout Pages
  needs for this route contract;
- writes `404.html` so unknown paths do not fall back to the home page; and
- copies the route-parity Worker to `_worker.js`.

Inspect the artifact and confirm that `_worker.js` and `404.html` exist while
`web.config` does not. Never deploy a partial or failed build.

Blog posts are kept outside this repository. Confirm that
`.build-runs/cloudflare-artifact/blog/feed.xml` contains `<item>` entries and
that the build did not warn about missing blog content. A build without posts
would remove every article from the live site; stop and restore the
`.blog-content` link or `STEAM_ENGINE_BLOG_CONTENT` before deploying.

If source files changed during the task, also run the repository's normal
`npm run build` before handoff as required by `AGENTS.md`. The normal build
validates and switches the local IIS preview; it does not replace the
Cloudflare artifact build.

## Review deployment state

Before uploading:

1. Inspect `git status --short` and the task-related diff. Deploy from the
   repository's `master` branch; merge pull requests and `catalog/<topic>`
   branches first.
2. Run `npx wrangler pages deployment list --project-name steam-engine`.
   Confirm the project exists, that its production branch is `main`, and note
   the source commit of the current production deployment.
3. Review `git log` and `git diff` from that commit to `HEAD` so that you know
   everything the upload will release, not only the current task.
4. If that range changes an API adapter URL or request contract, confirm that
   the new API version answers on the calculation Worker before uploading. The
   Worker must be deployed first; never publish a frontend that calls an API
   version the Worker does not serve.
5. Check that the GitHub Actions "Public repository checks" run for `HEAD`
   passed (`gh run list --branch master --limit 3`). Investigate a failure
   before deploying.
6. Record whether the tree is dirty. A deployment request does not authorize a
   commit, and a commit request does not silently authorize deployment.
7. If the tree is dirty, deploy only after the changed artifact has been
   reviewed. Pass `--commit-dirty=true` so Wrangler records that state instead
   of concealing it. Uncommitted files that are not part of the build, such as
   agent skills, still make the tree dirty.
8. Wrangler records only this repository's commit. Report the commit of the
   blog content used for the build in the handoff so that the release can be
   reproduced; do not write it into this repository.

## Deploy with Wrangler

For a clean tree, run:

```powershell
npx wrangler pages deploy .build-runs/cloudflare-artifact `
  --project-name steam-engine `
  --branch main
```

For an explicitly reviewed dirty tree, append `--commit-dirty=true`. Uploading
is an external side effect; request the execution approval required by the
environment immediately before the command.

Treat Wrangler's `Deployment complete` output as upload evidence, not as the
entire verification. Record the unique deployment URL it returns.

Every production upload, including advertising-only changes, uses this Pages
deployment path. A new Pages deployment is the shared cache-invalidation event
for the entire site; do not create a separate provider-specific purge path.

## Verify production

Confirm through the Cloudflare API or `wrangler pages deployment list` that the
newest `steam-engine` production deployment completed successfully. Then check
the production alias without following redirects automatically.

At minimum verify:

- `200`: `/`, `/juice`, `/nb/ohm`, `/blog`, a dated blog page, and a catalog
  detail page;
- `301`: `/default.asp` and `/index.html` to `/`, English calculator
  implementation suffixes to their calculator paths, `/catalog/battery` to
  `/catalog#batteries`, and the equivalent localized shortcut;
- `301`: `/juice.html` and `/juice.asp` to `/juice`.
- `404`: `/juice/`, `/blog/category/news`, `/404`, and a retired route.

When the release includes a new blog post, also check that its dated page
returns `200` and that it leads `/blog/feed.xml`. When it changes an API
adapter, open the affected calculator and confirm that it shows results.

For the redirects, compare the response status and `Location` header. Also open
at least one calculator in a browser when the deployment includes visible UI
changes. Stop and investigate if the unique deployment succeeds but the
production alias serves different content or route behavior.

## Handoff

Report:

- the production and unique deployment URLs;
- Cloudflare's deployment status;
- the build, route, link, and artifact validation results;
- representative live HTTP results;
- whether the deployed tree was clean or dirty;
- the previous production commit and the blog content commit; and
- any uncommitted files, permission changes, or propagation uncertainty.

Do not claim that a custom domain is live unless it was separately configured
and verified. Do not delete older deployments or the Pages project unless the
user explicitly requests that destructive operation.
